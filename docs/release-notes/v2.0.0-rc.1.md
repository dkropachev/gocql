# gocql v2.0.0-rc.1 (draft)

Draft notes for the first v2 release candidate. The Release workflow publishes
GitHub's generated notes (see `RELEASING.md`), which list merged pull requests
only. Once the release is published, add this text above them in the GitHub
Release description, and update it for later candidates.

v2 is a new major version with a new module path,
`github.com/scylladb/gocql/v2`, and a typed API for ScyllaDB and Apache
Cassandra. It is not source compatible with v1. Both versions can be imported
by one program, so applications can migrate one package at a time; the
[migration guide](https://github.com/scylladb/gocql/blob/v2.0.0-rc.1/docs/source/migrating-from-v1.md)
maps the most used v1 calls to v2.

```sh
go get github.com/scylladb/gocql/v2@v2.0.0-rc.1
```

This is a release candidate. The API may still change before v2.0.0 if
testing finds a problem; report issues at
https://github.com/scylladb/gocql/issues.

## Highlights

- **Typed statements.** A `cql.Statement[P, R]` declares its parameter and row
  types with explicit encoders and decoders, or with struct mappings
  (`cql.ParamsOf`, `cql.RowOf`) built once and checked against the server's
  metadata at prepare time. No per-call reflection.
- **Low-allocation execution.** `Prepared.Exec`, `One`, `Each` and `All` run a
  shared prepared statement with no per-call execution state, and a
  worker-owned `Query` reuses its parameter buffers and resolved options.
- **Streaming into caller storage.** `Session.PrepareStream` decodes rows into
  storage the caller seeds, page by page or incrementally with bounded memory
  (`exec.StreamOptions{Incremental: true}`).
- **Shard- and tablet-aware routing on ScyllaDB.** One connection per shard,
  shard-aware ports, tablet routing, and leader-aware routing for strongly
  consistent tables, behind one `routing.Policy`. On ScyllaDB servers that
  offer `TABLETS_ROUTING_V2_EXPERIMENTAL` (2026.3 and later with the
  `strongly-consistent-tables` experimental feature), the default policy sends
  requests to a `consistency = 'global'` keyspace, except those at `ONE` or
  `LOCAL_ONE`, to the tablet's Raft leader instead of letting a replica
  forward them.
- **Validated configuration.** `config.New(...).Build()` checks every setting
  and returns an immutable `config.Config`; request defaults live in
  `config.Profile`, per-call overrides in `exec.Options`.
- **Errors that say what happened.** Typed server errors in `cqlerr`,
  `cqlerr.KindOf` to tell transient failures from permanent ones, and
  `cqlerr.ExecutionStatusOf` to tell whether a failed write may have applied.
  `retry.Safe` retries a non-idempotent request only after a failure that
  reports it was not executed, or a read timeout that returned no data.
  Messages name every attempt's host and shard, never bound values; opt in
  with `ConfigBuilder.WithErrorStatementText` to add the statement's CQL text.
- **Observation.** `observe` hooks per request and per attempt, `metrics`
  snapshots, `log/slog` logging, `cqltrace` for server-side traces, and
  `Session.Subscribe` for topology, status and schema events.

## Performance

Throughput against gocql v1 (master `a61c57f`) and scylla-rust-driver
1.10.0, measured with the harness in `tests/driver-comparison/three`. Each
client gets half of one CPU (Go with `GOMAXPROCS=1`, Rust on a
current-thread runtime) against three ScyllaDB 2026.3.3 nodes, so client CPU
per operation is what limits the result. Protocol 4, `LOCAL_QUORUM`, RF=3,
one connection per shard, page size 32, no prefetch, compression, retries or
speculation; every read is validated. Closed loop, operations per second,
median of three rounds, v2 at `b5953cf`. The cluster was small (two shards
per node) and the host was shared, so compare the ratios, not the absolute
numbers.

| Workload | v1 | v2 | Rust | v2 / v1 | Rust / v1 | Client CPU µs/op (v1 / v2 / Rust) |
|---|---:|---:|---:|---:|---:|---|
| Prepared exec: 1 KiB point write, 64 workers | 43,152 | 53,145 | 67,741 | 1.23x | 1.57x | 11.4 / 9.2 / 6.6 |
| Select one: 1 KiB point read, 64 workers | 39,820 | 56,406 | 92,473 | 1.42x | 2.32x | 12.6 / 8.9 / 5.4 |
| Paged scan: 128 × 4 KiB rows per partition, 4 workers | 977 | 1,004 | 1,000 | 1.03x | 1.02x | 511 / 496 / 494 |
| Streaming the same partitions, v2 buffered / incremental | 977 | 831 / 727 | 1,000 | 0.85x / 0.74x | 1.02x | 511 / 597 and 685 / 494 |
| Unlogged batch of 8 rows, 8 workers | 16,830 | 15,922 | 18,700 | 0.95x | 1.11x | 27.3 / 29.5 / 19.5 |

- v2 needs 19 % (writes) and 29 % (reads) less client CPU per operation
  than v1, and the Rust driver 28 % and 39 % less than v2. Point-write
  rounds varied widely: v2 / v1 was 0.87x, 1.23x and 1.37x.
- On a paged scan all three drivers use their whole CPU budget and are
  within 3 % of each other.
- Streaming (`PrepareStream`) has 17 % (buffered) and 28 % (incremental)
  lower throughput than v2's own `Worker.Each` over the same pages, and
  uses 20 % and 38 % more CPU per operation. It bounds memory, not CPU;
  use `Each`, `All` or `Run` when pages fit in memory.
- v2 sends unlogged batches 5 % slower than v1 and uses about 8 % more CPU
  per batch (29.5 against 27.3 µs). v1's throughput rounds ranged from
  14,036 to 18,044, so the throughput gap is within noise; the CPU gap held
  in two of three rounds.
- An earlier run of the same harness, with an earlier v2 commit, on an
  isolated host (four shards per node, fixed CPU clock) found the same
  ordering: v2 / v1 of 1.33x for point reads, 1.31x for point writes,
  1.02x for a paged scan and 0.98x for batches.

Not measured:

- The harness has no streaming case for v1 or the Rust driver, so their
  streaming row repeats their paged scan.
- Latency at equal offered load: there was no open-loop run for this
  release candidate. Latency under the closed loop above is queueing, not
  service time, and is not reported.
- More than one client CPU, prefetch, Cassandra, protocol 5, compression,
  TLS and arm64.
- The `tests/bench` benchmarks measure v2 alone against recorded traffic
  and a fake node; they were not compared with v1 or Rust.

A warm execution of a reused prepared statement allocates nothing for an
exec or a single-row read, and one allocation per page after the first for
a paged scan (the paging state). A reused batch sent with `ExecBatch`
allocates nothing; `RunBatch` allocates three times, to register the rows
it returns. Unit tests in CI hold these counts, and streaming's
per-execution and per-page counts, as ceilings: the lowest of three
averages over 1,000 executions may exceed one by at most 0.2.

## Breaking changes from v1

Every v1 call site changes. In short:

- Module path `github.com/scylladb/gocql/v2`; Go 1.27 or newer. Build with
  Go 1.27.4 or later: go1.27.0 has standard-library vulnerabilities that
  go1.27.4 fixes. The module keeps `go 1.27.0` as its minimum and does not
  force a toolchain.
- `gocql.NewCluster` and `ClusterConfig` fields are replaced by the
  `config.New(...)` builder; `CreateSession` by
  `gocql.Connect(ctx, cfg)`.
- The dialect (`config.ScyllaV4`, `config.CassandraV4`, `config.CassandraV5`),
  the first argument of `config.New`, fixes the database and protocol version;
  nothing is negotiated, and
  protocols 3 and older are not supported.
- `session.Query(stmt, values...)` with `Scan`/`Iter` is replaced by typed
  statements, explicit `Session.Prepare`, and
  `Exec`/`One`/`Each`/`All`/`Run`/`RunPage`.
  Every call takes a `context.Context` first.
- Per-query setters (`Consistency`, `PageSize`, `Idempotent`, ...) become
  `exec.Options` fields; cluster-wide request defaults become a
  `config.Profile`.
- Host selection, retry and speculative execution policies are replaced by
  `routing.Policy`, `retry.Policy` and `retry.SpeculationPolicy`.
- Errors move to `cqlerr`; `gocql.ErrNotFound` from `Scan` becomes the `found`
  result of `One`. `ErrKeyspaceDoesNotExist` is gone, a write timeout's or
  failure's `WriteType` is a `cqlerr.WriteType` enum, and `cqlerr.ErrorMap` is
  keyed by `netip.Addr`.
- Schema metadata in `metadata` follows Go naming and types: `View` and
  `Index` name their keyspace and table like `Table` does (`Keyspace`, `Name`,
  `Table`, `BaseTable`), `Equals` is `Equal`, `TableOptions` spells
  initialisms (`GCGraceSeconds`, `BloomFilterFPChance`, ...), table and view
  IDs and `TableOptions.Version` are `cql.UUID`, and a column's clustering
  order is one `metadata.ColumnOrder` field.
- `cql.UUID` drops the version 1 accessors (`Time`, `Timestamp`, `Clock`,
  `Node`); they are on `cql.TimeUUID`, where `Clock` returns a `uint16` and
  `Node` a `[6]byte`, the types `cql.TimeUUIDWith` takes.
- `gocql.Type` and its `TypeInt`, `TypeAscii`, ... constants, a CQL type's
  kind, are `cql.Kind` and `cql.KindInt`, `cql.KindASCII`, ..., a `uint16`
  like the protocol's type ID (v1: `int`). Text and varchar are one kind,
  `cql.KindText`.
- The default consistency is `LOCAL_QUORUM` (v1: `QUORUM`).
- `ReconnectionPolicy` is `endpoint.ReconnectPolicy`, whose `Delay` numbers
  reconnections from 1 (v1's `GetInterval` counted from 0). Code that indexes
  a table of delays by the attempt number must subtract one.
- `USE` statements are rejected; set the keyspace in the configuration.
- `Marshaler`/`Unmarshaler` are replaced by `cql.Encoder`/`cql.Decoder` codecs.

## Known limitations

- Protocol 4 frame compression (LZ4 or Snappy) cannot be combined with
  incremental streaming; such a query fails with `cql.StreamCapabilityError`
  before it is sent. Buffered execution supports it.
- `cql.PageState` tokens are opaque server state and are not signed by the
  driver; authenticate or encrypt them before handing them to untrusted
  clients.
- ScyllaDB-only features (tablets, shard awareness, rate-limit errors, the
  CDC partitioner) have no effect on Cassandra. Settings that only one dialect
  supports, such as `WithClientRoutes` or `exec.Options.NowInSeconds`, fail at
  `config.ConfigBuilder.Build` or `CompileOptions` on the other dialect; see
  [server differences](https://github.com/scylladb/gocql/blob/v2.0.0-rc.1/docs/source/server-differences.md).
- Leader-aware routing for strongly consistent tables follows ScyllaDB's
  experimental `TABLETS_ROUTING_V2_EXPERIMENTAL` extension, whose name and
  format may still change. A batch goes to the leader of its first routed
  statement's tablet only; the tablets of its other statements are not
  considered.
- Cassandra and ScyllaDB return different rows for conditional statements and
  batches; decode them as the
  [lightweight transactions guide](https://github.com/scylladb/gocql/blob/v2.0.0-rc.1/docs/source/statements/lightweight-transactions.md)
  describes.
